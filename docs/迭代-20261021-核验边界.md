# 迭代报告：核验中的建议与事实边界

## 实验前登记

- 靶点：长稿件中把决策提醒当成未经证实的产品事实。原始记录：`final-wechat-travel-1792506250983`，原始结果目录 `output/final-runs/复赛-2026-10-20T14-24-10-927Z`。
- 诊断：原始核验把“重量只回答携带这一半问题”解释为量化断言，把“不默认两个 USB-C 能同时解决所有连接”解释为未经证明的否定。短句与完整长稿分开回放，判断是否与上下文有关。
- 假设：仅在独立核验提示中明确“指出证据不足不等于断言不支持”“比喻不等于量化”，并要求问题必须指出新增的可检验事实，可减少长稿误报，而不放过错误参数、版本混用、兼容承诺与体验推断。
- 唯一生产改动层面：`app/lib/agent.ts` 的 `verifyEvidence` 提示词。模型、调用参数、检索、证据、图片、输出结构不变。
- 固定样本：10个有标签短例（5正确、5错误）及1篇原始完整公众号稿，各重复2次。完整稿预先标注4处正常提醒和1处主观效果推断；不以问题总数下降作为成功标准。
- 成功判据：短例保持20/20；完整稿4处正常提醒的合计误报较基线降低至少50%，且两次重复各自都降低；完整稿的主观效果推断两次均被识别；没有调用失败。人工标准：提醒可保留自然表达，真正的参数、版本及兼容边界仍得到保护。
- 评测实现：`app/tests/verifier-calibration.live.mjs`。对比时必须具有相同 corpusHash。保留每条问题供复核。
- 预试发现：公开界面快照省略图片复核元数据，直接用于回放会制造图片误报。首次预试已标为无效并单独保存；正式实验改用私密持久化会话的完整输入，尚未修改生产提示词。之后冻结输入及标签，不根据结果更改。

## 元反思

展示快照不是执行快照。回放评测必须保留来源、型号和图片复核状态等影响决策的元数据；否则可能把评测输入缺陷误当成产品问题。

第二个问题是核验结论自相矛盾：基线第一次完整稿把蓝牙提醒列入问题，但该问题理由末尾又写“可保留；不列为问题”。这属于可观察的输出一致性缺陷，下一轮可优先检验核验输出契约，不能直接用字符串过滤或降低全部检查强度掩盖它。

短例前后均全对，长稿仍会波动，说明只测独立句子不足以代表真实创作流程。下一轮应继续保留完整长稿和真实错误对照；如需扩大标注范围，在新实验开始前独立登记，不追改本轮样本与判据。当前样本只覆盖一个型号的核验，不能声称已验证跨型号、问答或检索的整体可靠性。
