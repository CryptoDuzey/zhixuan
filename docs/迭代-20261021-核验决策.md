# 迭代报告：核验决策与理由一致性（第2轮）

## 1. 靶点与证据

上一轮正式基线 `output/iterations/verifier-calibration-20261021/baseline.json`，`real-wechat` 第1次：蓝牙提醒被放进 `issues`，但理由结尾写“属合理提醒，可保留；不列为问题”。应用把列表成员全部作为问题，无法区分模型在讨论疑点还是最终要求修改。这是输出决策表达的缺口；不通过关键词删除理由来掩盖。

## 2. 实验前登记

- 假设：给候选检查项增加明确的 `change/keep` 决策，模型可记录疑点被排除的原因；应用只将 `change` 转成问题，可消除“判为问题却又认可”的矛盾，同时保留真实错误。
- 唯一生产改动层面：核验模块的内部输出协议（协议说明与对应读取校验）。不改变事实判断规则、检索、输入证据、模型、温度、字数预算，也不增加模型调用或修改用户稿件。
- 固定评测集：沿用上一轮10个短例和1篇完整原稿；同一输入各重复3次。完整稿仍用原先4处正常提醒和1处真实错误标注，不能追改标签。
- 成功判据：短例30/30；真实错误短例15/15及长稿主观效果3/3检出；预标正常提醒误报不得比本轮基线增加；在基线能复现至少1条明确矛盾的前提下，候选3篇长稿中明确矛盾为0；无调用或协议错误。若本轮基线不能复现矛盾，不将“0对0”称为改善。
- 人工标准：逐条阅读长稿的问题与理由，“建议可保留”却仍要求修改才算决策矛盾；有版本或接口限制需要补充时，即使包含“建议”二字也不算矛盾。不能靠字面关键词替代人工判定。
- 独立审阅：另一个只读协作者复核上一轮矛盾例及本轮风险；不并行修改生产文件。
- 结果保存在私有本地 `output/iterations/verifier-decisions-20261021/`，脚本拒绝覆盖既有结果，捕获原始模型正文（不包含密钥与推理内容），便于核对决策在何处变化。模型配置用不含密钥的摘要核对。

逐条变化：

- `real-wechat` 基线第3次将“一半问题”、两个接口不应默认适配、蓝牙版本不等于适配三条正常提醒列为问题；候选三次均未列这些问题，误报有所下降。
- 原始稿中“标准屏版798 g的机身重量会直接影响你愿不愿意每天把它放进包里”为预标真实错误：重量证据不能证明携带意愿。基线三次都识别；候选仅第2次识别，第1和第3次漏检。这是决定回滚的失败变化。
- 候选第1次原始模型输出13个`keep`、0个`change`；第3次12个`keep`、0个`change`。两次均未提到该携带意愿主张，而非在读取结果时丢掉了`change`。两次返回的已确认编号中也没有该主张的C2。没有确认该主张，却没有给出问题，不能因此判为可靠通过。
- 短例中的错误重量、版本混用、兼容承诺、双屏能力及无负担效果前后均识别。短例保持全对，仍不能抵消真实长稿中的漏检。

人工标准结论：未通过。结构更明确没有带来可靠的全文审查；“问题变少”在这个案例里混合了误报下降与漏检增加。且本轮新基线没有稳定复现上轮的明确矛盾，因此也不能宣称该矛盾已消除。两组各重复3次，样本只覆盖一个型号，不作统计显著性或整体产品质量结论。

独立只读协作者复核全部6份长稿原始输出与26条最终问题，确认候选每次的最终问题均与原始`change`逐条对应，没有解析丢失；漏检主张未出现在`keep`中，不能描述为已审查后被认可。协作者同样建议回滚，并确认本轮基线没有明确的决定—理由矛盾。

## 5. 元反思

本轮揭示更具体的失败模式：模型可能只解释它容易证明的事实，跳过难以证明的主张。候选两次没有确认C2，也没有报告C2有问题；结果列表看起来更干净，但审查覆盖不完整。增加一个决策字段无法保证全文覆盖。

后续候选靶点是“每条产品主张是否得到明确处置”，而非继续扩写泛化提醒。需要先由人工明确哪些属于产品事实、哪些属于建议，并建立跨型号、问答与长短文的固定标注，再决定如何处理“未审查/无法确认”的主张；不能直接把所有未确认项都阻断，也不能静默当作通过。本轮没有实施这个新方向，遵守两轮无收益后的停止规则。

评测范围仍有限：字符串位置匹配仅用于预标5处的计数，无法评估全文所有事实，因此本轮同时保留原始输出并逐条阅读。以后的实验不能只用模型自己输出的已确认列表证明它没有漏检。
